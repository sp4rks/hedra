# Configuration store

`ConfigStore` defines its tenant collection and exposes a generic controller using a supplied backend. `config.tenants` is typed as `Controller<Tenant>` using plain tenant data and provides the same asynchronous [resource operations](collections.md#controller-operations) as application controllers. The controller receives no tenant model.

This store persists tenant configuration. Process settings and `Hedra.config` remain the responsibility of [server configuration](configuration.md).

## Create and retrieve a tenant

From the repository root with Bun and the project's dependencies installed, use the public exports:

```ts
import { ConfigStore, SqliteBackend, Tenant } from '#hedra.ts'

const backend = new SqliteBackend(':memory:')
const config = new ConfigStore(backend)
const CreateTenant = Tenant.omit({ id: true }).strict()

try {
  const input = CreateTenant.parse({ name: ' Acme ' })
  const tenant = await config.tenants.create(input)
  const stored = await config.tenants.get(tenant.id)

  // tenant and stored contain the generated UUID and name 'Acme'.
} finally {
  backend.close()
}
```

`Tenant` extends the shared `Resource` schema and is exported as both a Zod schema and its inferred TypeScript type.

| Field | Type | Behaviour |
| --- | --- | --- |
| `id` | UUID string | Generated by the default controller. Immutable; omit it from mutation payloads. |
| `name` | `string` | Required, trimmed and nonempty when the model-derived validator runs. |

Create and replacement require the name at compile time. Update accepts partial attributes. The caller's pure validator applies the model's name rules; the strict input subset above also rejects unknown fields. The controller preserves prepared attributes and independently rejects supplied IDs. `get`, `update` and `replace` return `null` for an absent ID; `delete` returns a boolean. No operation adds timestamps.

The [standalone example](../examples/04-config-store.ts) validates the input, checks the normalised name and retrieves the stored tenant. Run it without starting an HTTP server:

```sh
bun run examples/04-config-store.ts
```

It uses an in-memory database and should exit successfully without output or a database file.

## Share a backend with application resources

Pass the same backend to `ConfigStore` and `new Hedra({ backend })`. Multiple configuration stores sharing it see the same tenant catalogue. Application collections use their own named tables; the internal tenant collection uses `hedra_config_tenants`. Application registration reserves that exact name to prevent accidental overlap.

`ConfigStore` neither opens nor closes connections. Closing an app ends that app's controllers, while the borrowed backend and configuration store remain usable. The caller closes the backend after all its users finish; every store using it then loses storage access. See [backend ownership](backends.md#connection-ownership).

For persistence, construct the SQLite backend with a file path such as `.runtime/config.sqlite`. It does not resolve `HEDRA_SQLITE_PATH` itself. [SQLite storage](backends.md#sqlite-storage) describes paths, parent directories and container volumes.

## Validation and scope

The caller's validator rejects invalid tenant attributes before the controller is called. TypeScript checks controller data types, while runtime guards protect server-owned IDs and generic JSON/storage integrity. The controller does not trim names, apply name refinements or validate stored tenants against their model. Callers run a pure validator when those checks are needed. Updates remain atomic; failed guards or storage operations leave data unchanged. Errors propagate to the caller without constructing HTTP responses or terminating the process.

The backend contract is the generic `Backend` interface. There is no tenant-specific database method; the controller supplies the table name and resource data to ordinary storage operations. The former `ConfigBackend` and `insertTenant` interface are removed.

Creating a tenant definition does not add isolation to application resources. Environment resources, Web routes, other backends and legacy migration remain outside this increment.
