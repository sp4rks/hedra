# Configuration store

`ConfigStore` binds the tenant resource model to the generic controller using a supplied backend. `config.tenants` provides the same asynchronous [resource operations](collections.md#controller-operations) as application controllers.

This store persists tenant configuration. Process settings and `Hedra.config` remain the responsibility of [server configuration](configuration.md).

## Create and retrieve a tenant

From the repository root with Bun and the project's dependencies installed, use the public exports:

```ts
import { ConfigStore, SqliteBackend } from '#hedra.ts'

const backend = new SqliteBackend(':memory:')
const config = new ConfigStore(backend)

try {
  const tenant = await config.tenants.create({ name: ' Acme ' })
  const stored = await config.tenants.get(tenant.id)

  // tenant and stored contain the generated UUID and name 'Acme'.
} finally {
  backend.close()
}
```

`Tenant` extends the shared `Resource` schema and is exported as both a Zod schema and its inferred TypeScript type.

| Field | Type | Behaviour |
| --- | --- | --- |
| `id` | UUID string | Generated by the default controller. Immutable; omit it from mutation payloads. |
| `name` | `string` | Required, trimmed and nonempty. |

Create and replacement require the name. Update accepts partial attributes. The model removes unrecognised attributes, while supplied IDs are explicitly rejected. `get`, `update` and `replace` return `null` for an absent ID; `delete` returns a boolean. No operation adds timestamps.

The [standalone example](../examples/04-config-store.ts) checks the normalised name and retrieves the stored tenant. Run it without starting an HTTP server:

```sh
bun run examples/04-config-store.ts
```

It uses an in-memory database and should exit successfully without output or a database file.

## Share a backend with application resources

Pass the same backend to `ConfigStore` and `new Hedra({ backend })`. Multiple configuration stores sharing it see the same tenant catalogue. Application collections use their own named tables; the internal tenant collection uses `hedra_config_tenants`. Application registration reserves that exact name to prevent accidental overlap.

`ConfigStore` neither opens nor closes connections. Closing an app ends that app's controllers, while the borrowed backend and configuration store remain usable. The caller closes the backend after all its users finish; every store using it then loses storage access. See [backend ownership](backends.md#connection-ownership).

For persistence, construct the SQLite backend with a file path such as `.runtime/config.sqlite`. It does not resolve `HEDRA_SQLITE_PATH` itself. [SQLite storage](backends.md#sqlite-storage) describes paths, parent directories and container volumes.

## Validation and scope

Invalid tenant attributes reject before insertion. Updates validate the complete resulting tenant inside a transaction; failed mutations leave it unchanged. Validation, lifecycle and native storage failures propagate to the caller. Controller operations do not construct HTTP responses or terminate the process.

The backend contract is the generic `Backend` interface. There is no tenant-specific database method; the controller supplies the table name and validated resource to ordinary storage operations. The former `ConfigBackend` and `insertTenant` interface are removed.

Creating a tenant definition does not add isolation to application resources. Environment resources, Web routes, other backends and legacy migration remain outside this increment.
