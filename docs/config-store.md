# Configuration store

`ConfigStore` exposes tenant configuration through `config.tenants: ResourceOperations<Tenant>`, using a supplied backend. These programmatic operations require no Hono context and return resource data directly. [REST controllers](collections.md) have a separate interface and response envelopes.

This store persists tenant configuration. Process settings and `Hedra.config` remain the responsibility of [server configuration](configuration.md).

## Create and retrieve a tenant

From the repository root with Bun and the project's dependencies installed, use the public exports:

```ts
import { ConfigStore, SqliteBackend, Tenant } from '#hedra.ts'

const backend = new SqliteBackend(':memory:')
const config = new ConfigStore(backend)
const CreateTenant = Tenant.omit({ id: true, createdAt: true, updatedAt: true }).strict()

try {
  const input = CreateTenant.parse({ name: ' Acme ' })
  const tenant = await config.tenants.create(input)
  const stored = await config.tenants.get(tenant.id)

  // Both resources contain the generated metadata and name 'Acme'.
} finally {
  backend.close()
}
```

`Tenant` extends the shared `Resource` schema and is exported as both a Zod schema and its inferred TypeScript type.

| Field | Type | Behaviour |
| --- | --- | --- |
| `id` | UUID string | Generated by the operations helper and immutable. |
| `createdAt` | ISO timestamp | Assigned at creation and preserved thereafter. |
| `updatedAt` | ISO timestamp | Assigned at creation and refreshed on update/replacement. |
| `name` | `string` | Required, trimmed and nonempty when the caller's validator runs. |

Omit all three managed metadata fields from mutation payloads. Programmatic operations reject supplied managed fields. Create and replacement require the name at compile time; update accepts partial attributes. The caller's pure validator applies domain rules and normalisation; the strict subset above also rejects unknown fields. The helper preserves prepared ordinary attributes and protects generic JSON/storage integrity.

The [standalone example](../examples/04-config-store.ts) validates input, checks the normalised name and retrieves the stored tenant. Run it without starting an HTTP server:

```sh
bun run examples/04-config-store.ts
```

It uses an in-memory database and should exit successfully without output or a database file.

## Programmatic operations

All methods return promises. `ResourceOperations<T>` accepts a collection/table name and backend; it has no resource schema or HTTP context. `T` can describe plain data without declaring the shared `Resource` metadata fields. UUID and timestamp handling still runs independently of that type parameter.

| Method | Behaviour | Result |
| --- | --- | --- |
| `create(input)` | Insert attributes with generated UUID and audit timestamps. | Resource |
| `get(id)` | Read one resource by UUID. | Resource or `null` |
| `list(filter?)` | Match every scalar equality criterion, in insertion order. | Resource array |
| `update(id, changes)` | Shallowly merge supplied attributes and refresh `updatedAt`. | Resource or `null` |
| `replace(id, input)` | Replace ordinary attributes, preserving ID and creation time. | Resource or `null` |
| `delete(id)` | Remove one resource. | Boolean |

Update and replacement are atomic and never insert a missing resource. Replacement removes omitted optional attributes. List accepts the filter directly; it has no response envelope, pagination or sorting. These methods return stored data without REST output filtering; callers decide which attributes to expose externally.

## Share a backend with application resources

Pass the same backend to `ConfigStore` and `new Hedra({ backend })`. Multiple configuration stores sharing it see the same tenant catalogue. Application collections use their own named tables; the internal tenant collection uses `hedra_config_tenants`. Application registration reserves that exact name to prevent overlap.

`ConfigStore` neither opens nor closes connections. Closing an app ends that app's controllers, while the borrowed backend and configuration store remain usable. The caller closes the backend after all its users finish. See [connection ownership](backends.md#connection-ownership).

For persistence, construct the SQLite backend with a file path such as `.runtime/config.sqlite`. It does not resolve `HEDRA_SQLITE_PATH` itself. [SQLite storage](backends.md#sqlite-storage) describes paths, parent directories and container volumes.

## Validation and scope

The caller runs a pure validator for domain rules and for any desired stored-resource validation. The helper does not trim names or rerun domain refinements. Generic JSON, UUID and managed-field guards remain active; failed guards or storage operations leave data unchanged. Errors propagate without constructing HTTP responses or terminating the process.

There are no tenant-specific backend methods. The helper supplies the table name and resource data to generic `Backend` operations. Creating a tenant definition does not add application tenant isolation. Environment resources, automatic Web routes, other backends and legacy migration remain outside this increment.
